# Local multi-model AI assistant

Offline, zero-cost assistant tuned for this laptop (i7-1355U, 16 GB, no GPU). Each request is routed to one specialist model (code, math, security, writing, general), mostly in milliseconds by an embedding router; specialists load, answer and unload one at a time so everything fits in 16 GB RAM. Images are read by a vision model, your documents are searchable by meaning through a local vector database, and every stage of an answer is shown live. Rebuilt from `PROJECT_HANDOFF.md`.

## Setup (once)
1. Install Ollama from https://ollama.com, set the user environment variables `OLLAMA_NUM_PARALLEL=1`, `OLLAMA_FLASH_ATTENTION=1` and `OLLAMA_KV_CACHE_TYPE=q8_0`, then restart Ollama (see "Speed and RAM" below for why).
2. `setup.bat` creates `.venv` and installs `requirements.txt`.
3. `pull_models.bat` pulls the models (about 37 GB; the 14B is optional).
4. `.venv\Scripts\python.exe setup_check.py` verifies everything.
5. Optional: `powershell -ExecutionPolicy Bypass -File create_shortcut.ps1` puts a "Local AI" shortcut on the Desktop.
6. Optional: `powershell -ExecutionPolicy Bypass -File install_scheduled_task.ps1` for the daily 3 AM memory summary.

## Run
Double-click `start.bat` (or the Desktop shortcut). It starts Ollama if needed and opens http://127.0.0.1:8420.

## What is in the UI
- **Chat**: named chats that persist, grouped into projects (each chat keeps its own memory), live phase indicator and token streaming, Stop button, copy buttons, export to Markdown, search (Ctrl+K), new chat (Alt+N), light/dark theme. "Deep (14B)" skips the router and uses the 14B model (no tools).
- **System meters** in the sidebar, refreshed every 2 seconds: CPU load, RAM in use, CPU temperature (read from the Windows thermal sensor through the performance-counter API, no admin rights or extra software; amber from 80 °C, red from 90 °C, when the laptop starts slowing itself down), and how much RAM the loaded models hold.
- **Live step timeline** above every answer: each stage appears the moment it starts, with its own timer (choosing a specialist, freeing memory, loading and writing, every tool run, drafts, code checks, reviews, revisions, waiting for your push approval). Text that is not the answer streams live into an expandable panel on its step: deep-thinking drafts and reviews, a reasoning model's thoughts (if you configure one), tool output. When the answer is done the timeline folds into "N steps · time" and is saved with the answer, so it is still there after a reload.
- **Loads while you type:** a moment after you start typing, the app loads the model your message will need first (the router, or the specialist directly for tool requests and follow-ups), but only when nothing else is running and enough RAM is free (3 GB for the router, 7 GB for a specialist; never the 14B). It stays loaded for 2 minutes.
- **Automatic code checks** (`checks.py`): code blocks in an answer are checked without running them: Python is parsed and linted for real bugs (ruff: syntax errors, undefined names), HTML is checked for unclosed tags and the basics of a modern page (doctype, viewport, title, alt text), JSON is validated, and every calculation written out in an answer ("287 / 3.5833 = 79.9", also with brackets or in LaTeX like `\frac{287}{3.5833} = 79.8`) is recomputed from its numbers (a tiny + - * / evaluator, never `eval`) and flagged when wrong; so is a duration written next to two clock times ("from 9:40 to 13:15 is 4 h 15 min" -> 3 h 35 min, 24-hour or am/pm, across midnight). Shown as a timeline step in fast mode; fed back to the model in deep thinking.
- **Web pages / design:** requests for a web page, landing page, website or UI get one complete, self-contained, responsive and accessible HTML file. Every HTML code block has a **preview** button that renders it right in the chat (phone / tablet / full width), sandboxed and offline: it cannot reach this app or the internet. `create_document` can also save `.html` files. Downloads are always served as attachments, never rendered inside the app.
- **Switches under the message box** (remembered per browser):
  - **Deep thinking** (off = fast). Off: one pass. On, quality first, a **refine loop**: the model writes a draft, the code in it is checked automatically, the model reviews the draft against your original request (restated word for word in every round, so it cannot drift) and rewrites it, up to 3 rounds, stopping as soon as the checks pass and the review finds nothing, or when a revision leaves the answer unchanged (same final result) and the checks pass, because further reviews only nitpick (this cut a 17.5-minute run to 9.7). A revision that breaks code or markup is thrown away (the loop then tries again from the earlier version, telling the model which mistake to avoid); an arithmetic slip in a revision is not a reason to go back, because in real runs the earlier draft was wrong in a way no check can see (a wrong time span) and going back kept that wrong answer, so the slip is fed back as a certain error instead. A revision is also thrown away when it drops most of the answer's working (a real run kept "rewriting" a full solution as just "**Final Answer:** 79.8 km/h", which left the arithmetic check nothing to verify); the model is asked once more for the complete answer, otherwise the last complete version is kept. The reviewer is told to report only errors, not style. The model stays loaded between rounds, so each review re-uses the already-read prompt (a review took 19 s after a 1 m 44 s draft). In tool answers, a long document's content is reviewed once before it is saved. Expect 2-5x the time of fast mode.
  - **Keep model loaded**: the model stays in RAM for 10 minutes after an answer, so the next message skips loading and re-reading the prompt. Uses roughly 2-6 GB while loaded.
  - **14B model** as before.
  - **Long-term memory**: adds the daily summaries and, through the vector database, the most related exchanges from your *other* chats ("What is my cat called?" finds the chat where you said so). Every answered exchange is remembered in the background; deleting a chat deletes it from this index too.
- **How the chat keeps context and stays fast (loop engineering):** deep thinking's refine loop re-injects the original request in every draft, review and revision; a generation that falls into a repetition loop (a real run spent 8 minutes repeating one base64 fragment) is stopped at once, keeping the useful part and saying so; the last 6 real messages of the chat are re-injected into every prompt; every tool round restates your request; older tool results are shortened while the newest stays complete; an identical repeated tool call is skipped and the model is made to answer; a garbled repository path falls back to the one used earlier in the same answer; only the tool groups a request needs are listed in the prompt; short follow-ups ("make it shorter", "why?") reuse the previous route instead of calling the router.
- **Tools in chat** (for code, project, document and git requests): read PDF / Word / text files, search files, project tree, web search and page fetch, system info, ruff, pytest, git status/log/diff/pull/add/commit, and **create documents**: Word, PDF, PowerPoint, Excel, CSV, Markdown, HTML and charts, built from the content the model writes (`documents.py` + `officekit.py`). An answer may use up to 4 tool rounds (e.g. read a PDF, then create the report); creating a file or asking to push ends the answer at once. Created files appear as download buttons and are saved in `outputs/` (never overwritten).
  - Files are only created when you ask for one (a document, a file type, a report, a chart, save or export). A real run made `git_status_report.docx` when asked only for the git status; such a call is now skipped and the model answers in the chat.
  - Small models sometimes use the wrong reader (the Word reader on a `.md` file): every file reader now reads any supported file with the right method instead of failing, and the secret-file rule applies to all of them.
  - The assistant **never runs code it writes** and never deletes files. (The earlier separate "Agent" that wrote and ran programs was removed for speed; it is in git history, commit `e6c34db`.)
- **Tools tab**: git status/log/diff/pull and a reviewed, confirmed push; project file tree; **document library**; documents; find in files; web page; web search; a memory inspector.
- **Orchestration graph** above every answer: the stages it went through (Route → Vision → Retrieve → Draft → Tools → Check → Review → Revise → Answer), only those that happened, with ×n for repeats; the running stage glows, a stage with a problem turns amber or red. Live while it works and saved with the answer.
- **Images and screenshots:** attach (📎) or paste up to 3 images. Two stages: the vision model (`qwen2.5vl:3b`) first transcribes all readable text (code, error messages, numbers) and describes what matters for your question, streamed live; then the normal pipeline answers with that description, so a screenshot of a Python error is answered by the coding model, with tools and deep thinking available. Images are validated, shrunk to 1024 px (CPU time grows with image size) and never stored.
- **Document library (vector database, `semantic.py`):** index a folder of PDFs, Word files, notes or code (Tools tab, or ask the chat "index my notes folder at ..."), then ask "what do my notes say about ...": the chat calls `search_documents`, which finds passages by meaning, not exact words, and answers naming the file. Re-indexing skips unchanged files and forgets deleted ones. Secret-looking files are never indexed and secrets inside files are blanked out. Vectors live in `vectors.db` (SQLite) and are searched with numpy: exact cosine similarity, milliseconds for tens of thousands of passages, no extra server or heavy dependency.
- **Hybrid search:** the library combines meaning (vectors) with exact words (BM25 keyword ranking) by reciprocal rank fusion, so error codes, names and IDs are found even when their meaning is vague; results say "exact words" when they matched literally. A question that says "according to my documents" is told to search the library first (a small model once answered from general knowledge instead).
- **Big attachments:** an attached document longer than about 9,000 characters is no longer cut off at the end: the passages most relevant to your question are picked by vector search (the start is always kept), and the timeline shows "Picked the relevant parts of ...".

## The constitution and git pushes
`constitution.md` is the rulebook (Article 1: your data security comes first). It is **enforced in code** (`constitution.py`), so a model cannot argue its way past it, and it is deliberately **not** put into the models' prompts (when it was, small models refused ordinary requests "because of the constitution"). Read and manage it in the **Constitution** tab.

- **Lift the whole constitution:** one button switches off every rule, core ones included, for 5 to 60 minutes. A red banner shows the time left with **Restore now**; it also ends by itself and when the app restarts. A push still waits for your click. Every lift and restore is logged.

- **Pushing:** every push needs your click. The dialog shows the branch, remote, commits and files, then the constitution's verdict. A push is blocked if the commits (including old ones later "deleted") contain secrets (keys, tokens, passwords, private keys), include sensitive files (`.env`, keys, databases...), go to a host you have not approved (default `github.com`), target a protected branch (`main`, `master`), include a file over the size limit, or would force-push.
- **In chat** the assistant can `git_add`, `git_commit` (both refuse secrets) and `git_push_request`, which shows you the push dialog and only *asks*. It cannot push, force-push, or change the rules.
- **Documents:** nothing that looks like a secret is ever copied into a created document.
- **Your authority:** override any rule for one push with a checkbox; core rules (secrets, sensitive files, force-push) also need you to type `OVERRIDE`. Standard rules (protected branches, hosts, file size) can also be switched off or lifted for 5 to 60 minutes. Core rules can never be switched off.
- **Audit log:** every review, block, push, approval and override goes to `audit.jsonl` with secrets scrubbed (shown in the Constitution tab).
- **Untrusted content:** text from files, PDFs, web pages and tool output is labelled as data for the models, and a web search or URL containing something that looks like a secret is refused.
- **Cross-site guard:** a website open in your browser cannot click this app's buttons for you.
- Settings live in `constitution.json`; both it, the audit log and the chat database are in `.gitignore`.
- Read-only tools can read files your user account can read, except secret-looking ones; the rules are a strong safety net, not a sandbox.

## Speed and RAM (measured on this laptop)
- **Routing in milliseconds:** a rule catches unmistakable tool requests; otherwise the **embedding router** compares the message with ~110 labelled examples (`ROUTE_EXAMPLES`) using `nomic-embed-text` (0.27 GB, kept loaded); only when it is unsure does the router model decide. On 60 new held-out requests: router model alone 57/60 right at 13.4 s each; the hybrid 59/60 right, median 0.07 s (mean 2.2 s, because 1 in 6 messages still goes to the router model).
- **Load while you type** now predicts the *specialist* with the embedding router and loads it before you press Send (only with 7 GB RAM free and nothing running), with exactly the context window the request will use (a different size makes Ollama load it again). Measured: a coding question typed into a fresh chat started writing after **5.8 s**, with no load step.
- **Threads:** one per physical core (10). qwen2.5-coder:7b reading a 1,200-token prompt / writing, tokens per second: 4 threads 20.9 / 5.1, 6 (old setting) 23.6 / 5.4, 8 24.8 / 5.4, **10 28.0 / 5.6**, 12 26.7 / 5.0. Override with the `LOCAL_AI_THREADS` environment variable.
- **Flash attention + 8-bit KV cache** (Ollama settings above): reading 28.0 → 29.1, writing 5.6 → 5.9 tokens per second, 0.2 GB less RAM; a 16K context window now costs what 8K did.
- **Context window sized to the prompt:** Ollama silently drops the *start* of a prompt that does not fit (the instructions); every generation now picks the smallest window (4K, 8K, 12K, 16K) that holds the prompt plus room for the answer, and the timeline says when it grew.
- **RAM admission control:** before a model loads, the app checks it is downloaded and that its weights fit in free RAM; otherwise it uses the best pulled fallback that fits (`FALLBACK_MODELS`) and says so in the timeline, instead of paging for minutes. The 14B switch is your explicit choice and is never swapped.
- **The RAM trimmer never touches the model runner** (`llama-server`): before this fix it could push a model kept loaded (keep-warm, load-while-typing) out of RAM right before use.
- Chat history is read with a `LIMIT` query instead of loading a whole long chat on every message.
- **Models stay loaded for a follow-up:** after an answer the specialist stays in RAM for 3 minutes (15 with *Keep model loaded*); before a *different* model loads, every other one is unloaded first, so two big models never share 16 GB. The router model still unloads at once.
- **Prompt order for the prompt cache:** Ollama reuses the part of a prompt it has already read while the model is loaded. The system prompt now puts what never changes first and the per-request tool list last, and a follow-up keeps the previous tool list's order (new tools are appended), so the cached part stays valid. Measured: a prompt whose start matches the cache is read in 0.5-0.8 s instead of 22-28 s; in a real follow-up 525 of 1,465 tokens came from the cache and the 9 s load was skipped.
- **No tools when none are needed:** a coding question that mentions no files, folders, git, tests, web, documents, library or system gets no tool list and no tool rules (they were ~1,100 prompt tokens). "Write a Python function that merges two sorted lists" now starts writing after **16 s** cold (158 tokens read in 4.2 s, plus loading the model) instead of 55 s (1,281 tokens read in 41 s). Requests that need tools are caught by the tool-group patterns and the routing rules as before.
- **Follow-ups continue the cached conversation:** when the same chat continues with the same model, that model is still loaded and deep thinking is off, the follow-up is sent as a real conversation (earlier messages, the earlier answer, the new request) through Ollama's chat API, so everything before the new request is already in the model's cache and is not read again. Measured: "Now add type hints and a docstring" after a coding answer started writing after **3 s** (1,466 tokens read in 1.0 s) instead of about 55 s; "make it scarier" after a story, 7 s. In every other case (another model, a bigger context window, deep thinking, images, more than ~14,000 characters of conversation) the normal self-contained prompt is used, and the timeline says "Continuing the conversation" when it is not.
- **Every step shows Ollama's own numbers**, e.g. "read 822 tokens in 23.8 s · loaded in 9 s · wrote 249 at 5.4/s": a fast read of a long prompt means the cache was used.
- **Embeddings warm up at start-up** (in the background), so the first message is routed in about 0.1 s.

## Audit fixes
- The RAM trimmer did not protect the model runner (`llama-server`), so it could page out a loaded model right before use.
- `tools.write_file`, unused and unguarded (it could write anywhere), was removed.
- The PDF and Word readers did not apply the secret-file rule that `read_file` applies.
- An empty `LOCAL_AI_THREADS` setting crashed the app at start-up.
- The daily memory summary kept the *oldest* notes when there were many ("most recent" was cut off), and could pass secrets to the model; it now keeps the newest and blanks secrets.
- Unwanted files (a model creating a Word file nobody asked for) and the wrong file reader are now handled in code, see above.

## Notes
- Paths are relative to the project folder, so renaming the Windows user no longer breaks anything.
- `git push` is never model-callable and needs explicit confirmation.
- The 14B needs about 9 GB. With 5 to 8 GB free expect heavy paging and a first word after one to two minutes.
- **Math model: `qwen3:8b` with its thinking phase switched off**, chosen by a benchmark on this laptop (three math problems with known answers, same settings as the app):

  | Model | Right | Time per problem |
  |---|---|---|
  | qwen3:8b, thinking off | 2 of 3 | 1-3 min |
  | llama3.1:8b (old fast math model) | 1 of 3 | 40 s - 2.5 min |
  | deepseek-r1:8b (old deep math model) | 1 of 3 | 8.5 min; the other two had no answer after 11.5 min of reasoning |
  | qwen3:8b, thinking on | 0 of 1 | no answer after 12 min |

  Built-in reasoning phases are too slow on this CPU (about 4.5 words per second), so deep thinking uses the refine loop instead. Live check: the train-speed problem that every model got wrong in one pass is answered correctly (80.1 km/h) in deep thinking in about 6 minutes; the arithmetic check caught a wrong division and a later revision that broke it again was discarded. qwen3 likes LaTeX, so math answers are turned into plain text (`\frac`, `\boxed`, `$$`) before you see them. To bring `deepseek-r1` back, set it as `MATH_TASK` in `config.py` and add it to `THINKING_MODELS`. On general questions `llama3.2:3b` was as accurate as qwen3 and 2.5x faster, and for writing gemma2 and qwen3 were close, so those stay.
- Do not run `cmd /c start.bat` by bare name; use the full path or double-click (cmd mis-parses the bare name).
